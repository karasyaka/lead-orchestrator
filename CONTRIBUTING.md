# Contributing

Thank you for improving Lead Orchestrator. Keep changes narrow, evidence-based, and compatible with the skill's purpose: coordination must not become a new permission grant.

## Before proposing a change

1. Read [SKILL.md](SKILL.md), [VALIDATION.md](VALIDATION.md), and relevant host documentation.
2. Describe the concrete behavior or documentation problem with a reproducible example.
3. Keep unrelated formatting, refactoring, dependencies, and generated files out of the change.

## Behavior and documentation changes

Behavior changes need a stated scope, positive and negative acceptance cases, and validation matching the risk. Preserve explicit user boundaries, project instructions, approval gates, and executor preferences. Do not claim a provider capability merely because a command or delivery completed.

Keep installation paths host-specific and distinguish documented layouts from locally tested ones. Do not add performance, user, endorsement, accuracy, security-contact, or compatibility claims without evidence. Do not add private paths, account identifiers, session data, credentials, or unpublished links.

## Pull requests and license

Use the repository template. Include the smallest relevant validation result and say what was not run. A maintainer decides whether independent review is required before merging.

Keep the copyright and permission notices from the [MIT License](LICENSE) when distributing this package.
